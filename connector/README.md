# AeroE operator connector

A small Node.js service (no dependencies, Node 18 or later) that an operator runs between the AeroE Checklist app and
its own systems. It implements the interface in `../docs/INTEGRATION.md`:

| Endpoint | What it does |
|---|---|
| `GET /health` | Host health check, no token: `{ok:true}`. |
| `POST /defects`, `GET /defects` | Defect reports from the app (one file each under `data/defects`), listed newest first for the operator. |
| `POST /trend`, `GET /trend?rego=` | Engine trend readings, one JSON-lines file per registration. |
| `GET /sync`, `PUT /sync` | The pilot's flight preparation (plan, manifest, W&B, performance, open records, pilot, duty) as one JSON document per pilot ID, for the app's device-to-device sync. |
| `GET /ping` | Connection test; reports whether NAIPS and summaries are configured. |
| `GET /roster?pilot=&date=` | The pilot's flights for the day from `data/roster.json` (replace with a query to your rostering system). |
| `GET /fleet` | Fleet pack from `data/fleet.json`: registrations, checklist customisations, standard weights, duty limit. |
| `POST /records`, `GET /records` | Stores each uploaded flight record as `data/records/<id>.json` and checks a signed record's fingerprint. |
| `GET /notices`, `POST /notices/:id/ack` | Company notices from `data/notices.json`; read receipts appended to `data/acks.json`. |
| `POST /briefing` | NAIPS location briefing for departure, destination and alternates (TAF, METAR/SPECI, TTF, NOTAM, SIGMET), decoded, run through the alternate/holding/NOTAM rules, with a fuel plan and an optional plain-English summary. |
| `POST /fpl` | Files an ICAO flight notification through NAIPS (`submit-icao-fn`) and returns the FPL text; `dryRun: true` returns the preview only. |
| `GET /naips/status` | Authenticates the NAIPS account and returns the account name and message of the day. |

## Setup

1. Register a NAIPS account at https://www.airservicesaustralia.com/naips/ (the operator's account, or the pilot's own).
   The NAIPS SOAP interface used here is the one published at `https://www.airservicesaustralia.com/naips/briefing-service?wsdl`
   and `.../flight-notification-service?wsdl`; the request shapes in `naips.js` follow its schema. Airservices asks
   that third-party use be arranged with them – check the NAIPS terms before putting this into service.
2. Copy `.env.example` to `.env`, set the tokens, the NAIPS account and the app origin, then start it:

```bash
set -a; . ./.env; set +a
node server.js
```

3. In the app, Status › Operator link: enter the connector address, the pilot's token and pilot ID, then Test connection.

Run it behind HTTPS (a reverse proxy such as Caddy or nginx), because the app is served over HTTPS and browsers block
mixed content. `ALLOWED_ORIGIN` must be the app's origin exactly.

## The installed app does not need any of this

The iOS/Android build of the app (see `native/README.md`) calls NAIPS directly with the pilot's own login, using the
same code as this connector (`core.js`, `naips.js`, `met.js`, `rules.js` and `fuel.js` are bundled by
`tools/build-naips.js` into `data/naips-lib.js`). A connector is needed in a browser, and for operator features
(roster, fleet pack, notices, record upload). Edit the shared files here; the app bundle is regenerated by `node tools/build.js`.

## Run your own (a pilot's personal connector)

NAIPS cannot be called from a web page directly – Airservices' servers do not allow it – so the app always talks
to NAIPS through a connector. You do not need an operator to have one: this server runs happily with no roster,
no fleet pack and no operator NAIPS account, using the NAIPS login you enter in the app (Status › Operator link ›
Your NAIPS login), which it forwards per request and never stores.

The quickest free hosting is Render (https://render.com), which gives you HTTPS without any setup. One-click:
https://render.com/deploy?repo=https://github.com/swalksa350/AeroE-checklist (or your fork's URL). Or by hand:

1. Fork this repository on GitHub (or push a copy of the `connector/` folder plus the root `render.yaml`).
2. In Render choose New › Blueprint, pick your fork; it reads `render.yaml`. When asked, set `AEROE_TOKENS` to
   `yourname:` followed by a long random secret (that pair is your pilot ID and access token in the app).
3. When the service is live, note its address (`https://aeroe-connector-xxxx.onrender.com`).
4. In the app: Status › Operator link › Connector address = that address, Access token = the secret, Pilot ID = `yourname`,
   then Test connection, enter your NAIPS login and Test NAIPS login.

Persistent storage (records and flight-preparation sync): the free plan's filesystem is reset whenever the instance
restarts, including after it sleeps, so anything written to `DATA_DIR` is lost. To keep it: upgrade the service to the
Starter plan, add a Disk (Render dashboard › the service › Disks › Add Disk, mount path `/data`, 1 GB is plenty) and set
the environment variable `DATA_DIR=/data`. Records and the sync document then survive restarts and deploys.

Notes: the free plan sleeps after 15 minutes idle and the first request then takes up to a minute – press the
button again. Records uploaded to a free instance are not kept across restarts (your device keeps its own copies);
use a paid plan or a disk-backed `DATA_DIR` if the connector is to be the record store. Any other Node host
(Fly.io, Railway, a VPS behind Caddy) works the same way, and `connector/Dockerfile` builds a container for them.
`ALLOWED_ORIGIN` must match the app's origin exactly; set it to `*` only while testing.

## Preferred routes

`data/routes.json` holds the operator's preferred routes: `[ { "dep": "YSBK", "dest": "YBTH", "route": "BTH H65 CUL", "note": "company standard" } ]`.
`GET /routes?dep=&dest=` returns the matches; the app shows them in the planner beside the routes the pilot has used before.

## Briefing rules

`rules.js` applies the Australian aeroplane alternate and holding rules in a simple form: no TAF or a TAF not covering
ETA ± 30 min requires an alternate; forecast cloud more than SCT or visibility below the alternate minima (default
1,500 ft and 8 km, per aerodrome overrides in the request), thunderstorms, or crosswind/tailwind beyond the aircraft's
limits in the operative forecast require an alternate; TEMPO below minima carries 60 min holding, INTER 30 min, a bare
PROB 60 min; relevant NOTAMs (closures, lighting, navaid outages, fuel, obstacles) are flagged with the quoted text.
These are planning aids that the operator must align with its exposition and the current AIP; they are not a legal
determination and the raw products are always returned for the pilot to read.

## Summaries

With `ANTHROPIC_API_KEY` set and `npm install @anthropic-ai/sdk` done, `/briefing` adds a short plain-English summary
written by Claude (`claude-opus-5-5` by default). The prompt allows only statements traceable to the quoted products,
each tagged with its source, and the app shows the summary beside the raw text labelled as a draft.

## Tests

```bash
npm test
```

The tests run a mock NAIPS SOAP server and check the envelopes against the published schema, decode a sample briefing,
exercise the rules at several ETAs, and call the HTTP endpoints end to end.
