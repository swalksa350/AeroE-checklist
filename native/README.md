# AeroE Checklist – native apps (iOS and Android)

This folder wraps the web app in the parent folder into store-ready iOS and Android apps with
[Capacitor](https://capacitorjs.com). Nothing is rewritten: `build-web.js` copies the web app into `www/`,
turns off the service worker (the shell bundles everything), and bundles the offline speech engine so
there is no download step. The native projects in `ios/` and `android/` are committed; the copied web
files are not (they are regenerated by every sync).

## Pulling updates when Xcode has edited the project

Xcode writes your signing team into `ios/App/App.xcodeproj/project.pbxproj`, and git then refuses to pull a newer copy
of that file. Discard the local edit first (Xcode re-applies the team on the next open), then pull and sync:

```bash
cd ~/AeroE-checklist && git restore native/ios/App/App.xcodeproj/project.pbxproj && git pull && cd native && npm run ios
```

## Minimum iOS

The app and its pods are set to iOS 16.0 (the Podfile lifts the pods too). Xcode 26 and later refuse the iOS 13 minimum
that Capacitor 6 declares, which shows up as "The iOS deployment target ... is set to 13.0, but the range of supported
deployment target versions is ..." on every pod. If a future Xcode raises the floor again, change both the Podfile
`platform` line and the post_install hook, then run `npm run sync`.

## Opening flight plans from other apps

The iOS target declares the `.ozpln`, `.gpx` and `.fpl` document types and the Android manifest has VIEW/SEND
intent filters for them, so the installed app appears in the share sheet ("Copy to AeroE Checklist" on iOS,
Open with on Android). The file arrives through `@capacitor/app`'s `appUrlOpen` event, is read with
`@capacitor/filesystem` and imported onto the Plan page. After pulling this change run `npm install` in this
folder before `npm run ios`, so the Filesystem plugin is installed and synced.

## NAIPS direct

`capacitor.config.json` enables the Capacitor HTTP plugin, which routes the web app's `fetch` calls through native
code. That is what lets the installed app call NAIPS directly with the pilot's login (Status › Operator link), with
no connector. It has not yet been exercised on a device: after the first build, enter a NAIPS login and press Test
NAIPS login; if it reports that NAIPS did not accept the connection, check that the plugin setting survived `cap sync`.

## What you need on the Mac

- macOS with **Xcode** (App Store) and the command line tools (`xcode-select --install`)
- **CocoaPods** (`sudo gem install cocoapods` or `brew install cocoapods`)
- **Node.js 20+** (`brew install node`)
- An **Apple Developer Program** membership for the company, and the company's App Store Connect access
- For Android: **Android Studio** with an SDK installed

## Build and run on a connected iPad

```bash
git clone https://github.com/swalksa350/AeroE-checklist.git
cd AeroE-checklist/native
npm install
npm run assets          # generates app icons and splash screens from resources/ (first time, and after icon changes)
npm run ios             # builds www/, syncs it into the Xcode project and opens Xcode
```

In Xcode: select the `App` target → *Signing & Capabilities* → choose the company team (Xcode creates the
provisioning profile). Plug in the iPad, pick it as the run destination, press Run. The first run asks the
iPad to trust the developer certificate (Settings → General → VPN & Device Management).

Every time the web app changes, run `npm run sync` (or `npm run ios`) and build again in Xcode.

## Android

```bash
npm run android         # syncs and opens Android Studio; Run on a connected device or emulator
```

## Automatic TestFlight uploads (GitHub Actions)

`.github/workflows/testflight.yml` builds the iOS app on a GitHub macOS runner and uploads it to TestFlight on every
push to `main` that touches the app (web files, aircraft data, `native/`). The build number is the workflow run number
and the version comes from `changes.json`. Signing is automatic through an App Store Connect API key (Xcode's
cloud-managed distribution certificate), so nothing is exported from a Mac. One-off setup:

1. appstoreconnect.apple.com › Users and Access › Integrations › App Store Connect API › Team Keys › **+**: name
   `GitHub Actions`, access **Admin** (cloud signing needs it). Download the `.p8` (one chance only); note the
   **Key ID** and the **Issuer ID** shown above the list.
2. developer.apple.com › Account › Membership details: note the 10-character **Team ID**.
3. GitHub › the repository › Settings › Secrets and variables › Actions › New repository secret, four times:
   `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8` (open the .p8 in TextEdit and paste the whole contents, BEGIN and END
   lines included), `APPLE_TEAM_ID`.
4. Actions tab › TestFlight › Run workflow to try it. A run takes 10–20 minutes; the log ends with "Uploaded build N".
   Apple processes the build and the internal group with automatic distribution receives it.

The manual path below still works and is the fallback if a run fails (the log says why; the usual causes are a secret
pasted incompletely or the key not having Admin access). The repository is public, so macOS runner minutes are free.

## TestFlight and the App Store

TestFlight is the way onto an iPad that cannot enable Developer Mode (a company-managed device): the build is
installed through Apple's TestFlight app, not by Xcode. It needs a paid Apple Developer Program membership.

1. **Join the Apple Developer Program** at https://developer.apple.com/programs/enroll/ with the Apple ID you use in
   Xcode (about AUD 149 a year; approval can take up to 48 hours, an email confirms it). A Personal Team cannot upload.
2. **Point Xcode at the paid team.** Xcode › Settings › Accounts: the account now lists the paid team as well as the
   Personal Team. In the project (`npm run ios`, then App › Signing & Capabilities) change *Team* from the Personal Team
   to the paid one for the App target; leave *Automatically manage signing* on. Xcode registers the bundle id
   `au.com.aeroe.checklist` for that team.
3. **Create the app record** at https://appstoreconnect.apple.com › My Apps › + › New App: platform iOS, name
   "AeroE Checklist", primary language English (Australia), bundle id `au.com.aeroe.checklist`, SKU `aeroe-checklist`,
   full access. The name must be unique across the store; add a word if it is taken.
4. **Archive.** In Xcode set the run destination to *Any iOS Device (arm64)* (not My Mac, not a simulator), then
   *Product › Archive*. The Organizer opens with the archive; choose *Distribute App › TestFlight Internal Only › Upload*
   and accept the defaults. The first upload asks the export-compliance question only if `Info.plist` lacks
   `ITSAppUsesNonExemptEncryption` (it is set to NO here: the app uses only standard HTTPS).
5. **Wait for processing** (five to thirty minutes; App Store Connect emails when the build is ready).
6. **Add yourself as a tester.** App Store Connect › the app › TestFlight › Internal Testing › + › name the group,
   tick the build, add testers by Apple ID email (up to 100 internal testers; no beta review needed). Each tester
   gets an email invitation.
7. **On the iPad** install TestFlight from the App Store, open the invitation (or the TestFlight app) and tap Install.
   The app appears on the Home Screen like any other. Direct NAIPS calls work because it is the installed app.
8. **Updates.** Raise `CURRENT_PROJECT_VERSION` in `ios/App/App.xcodeproj/project.pbxproj` (every upload needs a
   higher build number), archive and upload again; TestFlight offers the new build on the iPad. A TestFlight build
   expires 90 days after upload, so upload at least that often.

If the company's device management blocks the App Store or TestFlight, no build can be installed on that iPad;
use the Pages web app with a connector (see `connector/README.md`, "Run your own") instead.

For the public App Store release in addition: screenshots (iPad 13" and 11", iPhone 6.7"), a privacy policy URL,
a support URL, the App Privacy questionnaire (no data collected: everything stays on the device), age rating, price,
and review notes saying the app works offline and the microphone is used only for on-device recognition of
checklist commands. External TestFlight testers (beyond the 100 internal) need a short beta review.

## Versioning

- The marketing version is `MARKETING_VERSION` in `ios/App/App.xcodeproj/project.pbxproj` and
  `versionName` in `android/app/build.gradle` (currently 2.1.0). Bump both with each store release and
  raise the build number (`CURRENT_PROJECT_VERSION` / `versionCode`) on every upload.
- The web app's own version (`changes.json`) is shown on the Status page and should match.
